## 三、分组详述

### A 组：经济与失败循环

#### 1. 破产循环收尾（P0｜原#1）
- **现状**：核心机制已完成。`BankruptcyManager.cs` 有宽限期(`graceCounter`/`maxGraceDays`)、逐级警告、宽限耗尽 Game Over；`LoanManager.cs` 贷款完整；负数金钱已支持。
- **缺口**：
  - 破产后**对话/叙事**接入（DialogueBridge 当前只是占位）。
  - 贷款 UX：何时弹 `LoanPanel`、利率提示、还款引导。
  - 破产→贷款→翻盘的**情绪曲线**与文案。
- **关键文件**：`Manager/BankruptcyManager.cs`、`Manager/LoanManager.cs`、`UI/BankruptcyPanel.cs`、`UI/LoanPanel.cs`、`Documents/破产结算系统设计.md`
- **建议**：先玩一遍走查现有流程，列出"还差哪几句话/哪几个弹窗"，再补对话与平衡，**不重写系统**。

### B 组：难度与平衡

#### 2. 难度过高（P0｜原#2）
- **现状**：近期已有 "Rebalance Halfway" 提交，说明在调，但仍偏难。
- **要做**：

  - 建一张**可调参数清单**（哪些在 Inspector、哪些在公式里），集中调。
  - 可考虑：开局宽限、前几天保底客流、贷款门槛降低。
- **关键文件**：`Data/ShelfArchetypes.cs`(公式)、`Customers/Spawner/CustomerSpawner.cs`(客流)、`Manager/DayLoopManager.cs`(结算)、`Services/FameCalculator`
- **依赖**：与 #3 结算改造、#1 贷款 UX 联动；最好放进 #4 内测一起验证。

### C 组：反馈系统

#### 3. 每日结算改造（P0｜原#5）
- **现状（比预期完成度高）**：已有**新版** `NewDailySettlementPanel.cs`，自带：销售额/奖励收入/维护费/金钱变化(正负色)/累计收支/今日声望/顾客数/顾客升级明细，外加 **7天趋势折线图 + 品类饼图 + 热销 Top3**（XChart）。数据与可视化基本齐全。
- **真正的缺口 = 你的三问里的"为什么 / 玩家为何需要"**：
  - 图表都在，但**没有"所以我下一步该做什么"的解读**。
  - **要做**：给关键数字加一句可行动解读（如"维护费占净收入 60%→考虑拆冷门货架"），把结算从"总结面板"变成**下一天的决策入口**。
  - 可补充字段：客单价、转化率(进店/购买)、与昨日对比 Δ。
- **关键文件**：`UI/NewDailySettlementPanel.cs`(新版主体)、`UI/DailySettlementPanel.cs`(旧版)、`Manager/DayLoopManager.cs`(`OnDailySettlement` 数据源)、`Documents/结算面板设计.md`
- **负责人**：🟩设计定解读文案为主，🟦Claude 可补聚合字段与挂接。

### E 组：任务与剧情

#### 5. 购买新楼层 Quest 线（P1｜原#7）
- **现状**：`WorldGrid.cs` 有 FloorLevel 体系、`ConstructionManager` 支持跨楼层，但**没有"购买/解锁楼层"的交易或 quest**。楼层目前是直接可建空间，非付费解锁。
- **要做**：
  - 楼层解锁机制（花钱/声望解锁上层）。
  - 配套 Quest 线（引导玩家攒钱→解锁→扩张）。
- **关键文件**：`Runtime/WorldGrid.cs`、`Runtime/ConstructionManager.cs`、`Quest/QuestManager.cs`、`Data/QuestDefinition.cs`
- **依赖**：需先定楼层解锁的数值与门槛（与 #2 难度耦合）。

#### 6. 剧情深化（P1｜原#4）
- **现状**：DialogueBridge(48 文件) + Quest 系统活跃开发中，已有教程/任务对话框架。
- **要做**：更多/更深/更复杂的剧情分支。属于**内容产出**，框架已具备。
- **依赖**：与 #7 任务差异化、#13 marker 精简强相关——剧情扩张前最好先理清 marker 体系。

#### 7. Achievement 系统 UI + 任务差异化（P1｜原#3）
- **现状**：**无独立成就系统**，成就职责目前由 Quest 顶替。
- **决策点**（需先定）：
  - 方案A：新建独立 Achievement 系统（与 Quest 并列）。
  - 方案B：在 Quest 上分类型（主线/支线/成就/挑战）实现"差异化"，复用现有 UI 框架。
  - **建议 B**：成本低、与"任务差异化"诉求天然契合。给 `QuestDefinition` 加 `questType` 枚举，UI 按类型分区/分样式。
- **关键文件**：`Data/QuestDefinition.cs`、`Quest/*`、`UI/Quest/*`(QuestLogPanel/QuestTrackerPanel 等)

#### 13. 精简 Quest activation marker 脚本（P2｜原#8a，技术债）
- **现状/问题**：`activationMarker` 是 `TutorialMarker` 巨型 enum，被**序列化为 int 存进 .asset**，同时驱动 Quest 激活 + 教程触发 + Dialogue Lua 变量**三套系统**，`TutorialMarkerBridge` 双向同步加重耦合。增删/重排成员易产生 enum alias 隐蔽 bug（见 CLAUDE.md 警告）。
- **要做**：解耦——让 Quest 激活不直接依赖巨型 enum，或拆分 enum 职责。
- **关键文件**：`Manager/TutorialMarker.cs`(114 个 marker，196 行)、`DialogueBridge/TutorialMarkerBridge.cs`、`Quest/QuestLogicManager.cs`、`Data/QuestDefinition.cs`(`activationMarker`/`completionMarker`/`failureMarker` 字段)
- **风险**：动 enum 会牵动大量 .asset，需谨慎+全量搜索引用。**建议在 #6 剧情大扩张前做**，否则越拖越贵。
